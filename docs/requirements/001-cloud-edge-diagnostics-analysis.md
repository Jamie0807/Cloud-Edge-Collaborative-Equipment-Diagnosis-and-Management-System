# 001 云边协同设备诊断管理：业务需求分析

**状态：** Approved decision baseline — 业务实现尚未开始。
**来源：** 上游需求输入、`AGENTS.md` 与已批准的研发治理基线。
**目的：** 将业务需求转为可审阅、可拆分、可持续演进的正式产品需求基线。

**决策确认记录：** D-001～D-005、D-009、D-010、D-014 由用户逐项确认；D-006 由用户确认采用 PostgreSQL；D-007、D-008、D-011～D-013 由用户授权基于调研采用本文件中的推荐方案。该授权仅冻结需求决策，不代表已开始业务编码。

## 1. 问题与边界

系统用于将三类感知终端采集的文件和元数据，经站内边端接入、保存、标准化和模拟分析后，可靠上报到云端，由云端保存、查询并在 Web 管理端展示。重点是可运行的主链路、可解释的数据归属、基本错误处理和可验证测试，不是精美 UI 或真实 AI 模型。

业务边界不可跨越：终端模拟器只访问边端；边端不让云端直接读取其本地文件或数据库；Web 只经云端 API 查询，不直接访问数据库。该特性应在已有治理基线和本 feature 的批准规格之后才进入代码实现。

## 2. 领域对象与身份语义

| 对象                            | 核心职责                                     | 必须标识                 | 关系                                                               |
| ------------------------------- | -------------------------------------------- | ------------------------ | ------------------------------------------------------------------ |
| 被监测设备（Asset）             | 被诊断的电力设备                             | `assetId`                | 一个设备可关联多个终端和多个诊断事件                               |
| 感知终端（Terminal）            | 采集一种模态的数据并发送心跳/文件            | `terminalId`             | 归属一个边端；配置关联站点、模态和采集周期                         |
| 边端节点（Edge）                | 终端接入、文件保存、标准化、分析、缓存、上报 | `edgeId`                 | 服务一个或多个终端；属于一个站点                                   |
| 检测/诊断事件（Event）          | 一次采集及其产生的诊断结果                   | `eventId`                | 关联恰好一个 asset、terminal、edge；可带一个原始文件和一项分析结果 |
| 原始检测文件（Evidence）        | 终端采集的图片或文件                         | `eventId`、存储 URI/路径 | 先由边端安全保存，再作为分析证据及云端详情引用                     |
| 模拟算法结果（Analysis Result） | 对单项文件的诊断输出                         | `eventId`                | 含缺陷类型、置信度、严重等级、分析时间和错误信息（若失败）         |
| 边端运行状态（Edge Status）     | 云端判断边端是否在线的心跳载荷               | `edgeId`                 | 含站点、CPU、内存、GPU/NPU、上报时间、最后接收时间                 |

四个 ID 的语义必须独立，禁止把任一 ID 派生为另一个 ID 或仅保留组合字符串：

- `assetId`：被监测设备的业务主键，回答“哪台设备被诊断”。
- `terminalId`：采集装置主键，回答“哪个终端采集”。
- `edgeId`：边端节点主键，回答“由哪个站内节点接入、分析和上报”。
- `eventId`：一次检测事件的全链路唯一键，回答“这是哪一次采集/诊断”，也是重试幂等键的候选。

每个跨服务心跳、上传、缓存记录、云端诊断记录、查询响应都须分别出现与自身语义相符的 ID 字段；即使查询只按其中一项筛选，响应也不得省略其余关联 ID。

## 3. 端到端业务链路

```text
终端配置与本地测试文件
  ├─ 每 10 秒心跳 ───────────────────────────────> 边端：记录 terminal 状态/lastSeen
  └─ 按模态采集文件+元数据 ──────────────────────> 边端：校验、标准化、安全保存
                                                        │
                                                        ├─> 模拟算法：单项分析
                                                        ├─> 待上报缓存（outbox）
                                                        └─> 边端状态 + 诊断结果 ──────> 云端：持久化、幂等接收
                                                                                           │
                                                                                           └─> Web：列表、筛选、详情/证据地址
```

### 3.1 终端到边端

至少模拟三台可配置终端：红外、声纹、局放。它们每 **10 秒**发送一次心跳；红外每 **5 秒**、声纹每 **20 秒**、局放每 **60 秒**生成一次检测数据。每次采集应携带文件和可验证元数据，至少含 `assetId`、`terminalId`、`edgeId`、`eventId`、站点、模态、采集时间和原始文件名/类型。终端不能绕过边端向云端发送任何业务载荷。

边端记录 `terminalId`、模态、最后在线时间和运行状态；对上传执行必填字段、ID 一致性、模态白名单、时间格式、文件大小/类型、文件名和路径安全校验。成功后保存原始文件，生成规范化元数据，保留原始 `eventId`。

### 3.2 边端分析与缓存

边端把其受控目录中保存的文件路径，以及 `assetId`、`terminalId`、模态传给模拟算法。算法不需真实模型，但必须：验证输入；为成功分析返回缺陷类型、置信度和严重等级；为不可处理输入返回可记录错误；写入不含敏感数据的关键日志。

边端把规范化检测数据、分析结果和证据引用组装为标准化诊断结果，先写入本地待上报缓存，再由上报任务尝试发送。缓存记录应可辨识待发送/发送中/成功/可重试失败/终止失败，且把 `eventId` 作为唯一业务键，避免网络重试产生重复业务事件。

边端还须定时上报自身状态：`edgeId`、站点、CPU、内存、GPU/NPU、上报时间。题目未给出状态上报频率；为满足云端 60 秒离线判定，推荐默认 **10 秒**，且允许配置。

### 3.3 边端到云端与云端查询

云端接收边端状态并保存 `edgeId`、站点、最后在线时间和在线状态；距最后成功接收心跳 **超过 60 秒**时将该边端视为离线。时间比较应在云端执行，使用统一 UTC 时间源，页面状态以云端计算结果为准。

云端接收并幂等保存诊断结果，至少持久化四个 ID、模态、缺陷类型、置信度、严重等级、发生时间、分析/接收时间和证据文件地址。它管理设备、终端和边端之间的关系，并支持按设备、终端、边端、模态、时间范围查询。Web 通过云端 API 展示边端列表、诊断列表、详情和筛选结果。

## 4. 功能需求

## 6. 已确认约束与范围外

已确认：推荐技术方向是 Vue、Spring Boot、PostgreSQL、Python，允许 Docker；云端后端和 Web 分别要求 Spring Boot/PostgreSQL/Vue；边端可由 Python、Java 或其他适合技术实现；通信方式由实现者选择并说明。

本初稿和后续首个 feature 不把下列内容当作必做：真实硬件接入、真实深度学习推理、生产多租户、复杂权限模型、跨站点高可用、自动部署、精致视觉设计、终端直接访问云端、云端直接读取边端文件系统。

## 7. 已确认决策与实现约束

| 决策                       | 尚未确认内容                         | 推荐值与理由                                                                                                                                                                                           |
| -------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D-001 终端↔边端通信        | HTTP、MQTT 或其他协议                | **HTTP REST + multipart/form-data**；心跳 JSON、文件上传 multipart。便于标准化契约、鉴权、错误处理与运维观测。                                                                                         |
| D-002 边端↔云端通信        | 同步 API、消息队列或混合             | **HTTPS REST + 本地 outbox**；诊断结果携带 idempotency key `eventId`，在网络不可用时指数退避重试。体量适合题目，不需引入消息中间件。                                                                   |
| D-003 边端技术             | Python、Java 或其他                  | **Python + FastAPI**；与模拟器/算法同语言，文件和调度实现快速。该选择仍需确认。                                                                                                                        |
| D-004 云端技术             | Spring Boot 的具体版本、ORM/API 形式 | **Spring Boot REST + JPA**，使用统一异常响应和 Bean Validation；符合题目并便于 JUnit 测试。                                                                                                            |
| D-005 Web 技术             | Vue 具体构建和状态方案               | **Vue 3 + TypeScript + Vite**，轻量组合式 API；避免为三个页面引入重型状态框架。                                                                                                                        |
| D-006 数据库与迁移         | 数据库版本、关系模型、迁移工具       | **PostgreSQL 18 + Flyway**；对 `eventId` 设置唯一约束，关系表/外键保留资产、终端、边端独立身份；JSONB 仅用于确有演进需求的扩展载荷，不替代核心列。                                                     |
| D-007 文件存储             | 云端只保存路径、上传副本或对象存储   | **边端受控本地目录保存原始文件；云端使用 MinIO/S3 兼容对象存储，保存对象 key、SHA-256 和媒体元数据**。详情访问时由云端按权限生成短时 presigned URL，不暴露边端路径或永久公开 URL。                     |
| D-008 鉴权                 | 终端、边端、Web 的身份机制           | **本地使用每个服务独立的环境注入服务令牌；生产使用 mTLS 或短期服务令牌，Web 使用 OIDC Authorization Code + PKCE，云端校验 JWT**。禁止硬编码密钥、将令牌写入 URL 或日志。                               |
| D-009 `eventId` 生成和幂等 | 由终端、边端还是云端创建             | **终端在采集时生成 UUIDv7，边端和云端原样保留；云端以 `eventId` 唯一约束和幂等响应去重**。重发同事件应返回已接收而非创建副本。                                                                         |
| D-010 心跳时间与离线       | 终端离线阈值、边端状态间隔、时钟责任 | **终端/边端均由各接收方记录接收时间；云端以自身接收时间、超过 60 秒判边端离线；边端状态上报默认 10 秒；终端离线阈值为 60 秒。**                                                                        |
| D-011 重试与失败终态       | 次数、队列顺序、人工处理             | **outbox 状态为 `PENDING/SENDING/RETRYABLE/FAILED/SENT`；网络错误、408、429、5xx 可重试并遵守 `Retry-After`，指数退避+全抖动，最多 10 次；明确 4xx 校验/鉴权错误不自动重试，记录原因并提供人工重放。** |
| D-012 文件与算法失败       | 是否上报失败事件、保留周期           | **文件校验失败在边端拒绝且不创建业务事件；算法失败保留已验证证据并创建可查询 `FAILED` 事件及机器错误码，不伪造成功；仅标记为瞬态的算法基础设施错误允许重试。**                                         |
| D-013 查询/分页            | 排序、默认时间窗、分页格式           | **服务端页码分页，默认 `page=1,size=20`，`size` 最大 100；按 `occurredAt DESC,eventId DESC` 稳定排序；过滤条件 AND 组合；默认最近 30 天；时间范围使用 UTC `[from,to)`；空结果返回 `items:[]`。**       |
| D-014 资源指标             | CPU/内存/GPU/NPU 的采样口径          | **记录利用率或可用量并带采样时间和“不可用”状态；没有 GPU/NPU 时明确 null/unsupported，而非虚构值。**                                                                                                   |

## 8. 风险与缓解

| 风险                   | 影响                         | 缓解                                                                                                  |
| ---------------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------- |
| 多运行单元并行交付风险 | 主链路或可靠性未打通         | 先以一个事件的红外 happy path 建立契约和可观测链路，再配置化复用到声纹/局放；每阶段必须保持回归门禁。 |
| 文件访问授权和过期策略 | 详情证据地址失效或越权       | 将对象 key/hash、短时 presigned URL、授权校验和审计字段纳入契约/集成测试。                            |
| 网络重试导致重复诊断   | 数据重复、列表错误           | D-009 的 `eventId` 唯一约束、边端 outbox 和幂等 API 是实现前置条件。                                  |
| 时钟偏差使离线误判     | 在线状态不可信               | 接收方记录服务器接收时间，统一 UTC；接口和页面展示阈值、最后接收时间及数据来源。                      |
| 终端上传不受控文件     | 路径穿越、磁盘耗尽、恶意内容 | 白名单、大小上限、随机存储名、受控目录、拒绝客户端路径；后续可补恶意文件扫描。                        |
| 将 ID 混用或省略       | 查询/追溯错误，违反项目约束  | 契约 schema、数据库列、日志字段和端到端测试都断言四个 ID 独立存在。                                   |
| 云端/边端技术选择延误  | 扩展实现范围                 | 已锁定 D-001 至 D-014，并通过 ADR、spec、plan、tasks 保持单一决策来源。                               |

## 9. 推荐的首期交付策略

建议采用“单一可验证主链路优先，三种模态配置化复用”的方案：Python/FastAPI 边端接收 HTTP multipart，使用受控本地文件目录和 SQLite 或同一边端轻量持久 outbox；Spring Boot/PostgreSQL/Flyway 云端提供幂等 REST API；Vue 3/Vite 三页管理端；开发环境 MinIO 提供 S3 兼容证据存储；Docker Compose 用于可复现启动。该方案不改变题目要求，且把通信、存储、重试、离线和查询责任清楚分离。

实现任务可以进入计划评审，但业务编码仍必须遵循批准后的 `spec.md`、`plan.md`、`tasks.md`、TDD 和 worktree 约束；容量、RTO/RPO、备份恢复、保留删除期限等生产参数在实现对应任务前必须补齐。
