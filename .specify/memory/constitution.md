# 项目 Constitution：云边协同设备诊断系统

> 状态：初始化基线，适用于后续 feature。本文定义约束，不宣称业务功能已经实现。
> 本文由已批准的治理设计第 5 节转化而来；bootstrap 的落地和证据见
> [`specs/000-bootstrap/spec.md`](../../specs/000-bootstrap/spec.md)、
> [`plan.md`](../../specs/000-bootstrap/plan.md) 和 [`tasks.md`](../../specs/000-bootstrap/tasks.md)。

## 原则 1：规格先于实现

- **强制要求：** 没有已确认的 spec、验收标准和 plan，不得编写生产代码；每个 feature 必须保留 `spec.md`、`plan.md`、`tasks.md`。
- **验证方式：** 审查任务变更是否能从 `spec → plan → tasks → files → tests` 追踪；缺任一产物则拒绝进入实现阶段。

## 原则 2：测试先于代码

- **强制要求：** 新行为必须先写能表达验收标准的失败测试（RED），再写最小实现（GREEN），最后重构；覆盖成功、非法输入、异常和关键空/加载/错误状态。
- **验证方式：** 检查任务记录中的 RED/GREEN/REFACTOR 证据，并运行适用的 Vitest、Playwright、JUnit 5、pytest 或契约测试。

## 原则 3：边界清晰

- **强制要求：** 服务通过明确契约通信，禁止跨服务直接读库或绕过边端链路；终端模拟器只访问边端，前端不直连数据库。
- **验证方式：** 审查架构、接口和依赖图；运行契约测试，确认 `assetId`、`terminalId`、`edgeId`、`eventId` 保持独立语义。

## 原则 4：可验证交付

- **强制要求：** 完成声明必须由新鲜命令输出、测试结果或构建证据支持，不得以“应该通过”代替证据。
- **验证方式：** 交付报告逐项列出命令、实际结果、未覆盖项和环境限制；运行 `git diff --check` 并检查报告与 diff 一致。

## 原则 5：自动化门禁

- **强制要求：** push 和 PR 必须通过格式、拼写、静态检查、测试和构建；`pnpm validate` 是唯一全量质量入口，任一子命令失败都必须失败退出。
- **验证方式：** 检查 `.github/workflows/ci.yml` 的 `push`/`pull_request` 触发器和门禁，运行 `pnpm validate` 或记录清晰的环境限制。

## 原则 6：可追溯变更

- **强制要求：** 需求、计划、任务、文件、测试和验收结果必须可以互相追踪；长期架构决策补充 ADR。
- **验证方式：** 审查 feature 产物的交叉引用、文件映射、测试映射和验收证据；检查相关 `docs/adr/` 记录。

## 原则 7：安全默认

- **强制要求：** 密钥不入库；输入、文件上传、路径、元数据和依赖必须经过安全边界检查；日志不得泄露凭据。
- **验证方式：** 检查 diff、日志和配置中的疑似密钥，审查输入校验/路径处理/依赖检查，并运行项目安全门禁（若已配置）。

## 原则 8：可运行优先

- **强制要求：** 本地提供统一启动、检查、测试和健康检查入口；服务边界和运行前置条件必须记录。
- **验证方式：** 运行对应入口和健康检查，审查架构文档与 runbook 是否说明安装、启动、联调和排障路径。

## 原则 9：AI 受约束协作

- **强制要求：** AI 必须先读取规范和 spec，只修改任务声明的写集，不扩大权限、范围或外部动作；使用隔离 worktree。
- **验证方式：** 检查 agent 报告中的 worktree、修改文件、命令和剩余风险；用 `git status`/`git diff` 核对写集无越界。

## 原则 10：人工最终决策

- **强制要求：** 架构、范围、破坏性操作、外部发布和合并由用户确认；agent 不自动 commit、push、创建 PR 或改写历史。
- **验证方式：** 审查操作记录和 Git 状态，确认未执行禁止动作；需要决策的事项必须列为待用户确认项或 ADR。
